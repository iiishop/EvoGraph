# Retained acceptance guard

`retained_acceptance` is one required deterministic harness plugin. Policy v7,
checker v13 and compiler protocol v4 invalidate earlier certificates for current
publication; historical review packets and raw output remain readable unchanged.

At new request admission, CandidateStore mechanically captures every canonical
active claim and every active claim in the exact retained entry candidate. The
latter are labeled `staged_draft`, never implicitly approved requirements. A new
job starts from its current saved entry; later phases of that same job reuse the
identical entry. Intermediate generated additions do not join it. Legacy
same-job continuation requires the exact original job-entry record pin.

The admission contains immutable behavior IDs/hashes, original binding projections,
existing predecessor record pins, and hashes of original source/requirement/process
history. Existing Project history remains the text authority. Change dispositions
replay from the existing append-only compiler audit; there is no parallel mutable
acceptance ledger. Admission and audit deletion/mutation are checked under the
existing candidate writer transaction and again at publication.

Unchanged same-key claims get a server-derived retained disposition. The optional
`ContractDelta.acceptance_changes` array supplies affected baseline IDs,
retained/replaced/retired disposition, active witness keys, optional acceptance
stage correspondence, change kind and a bounded reason. Existing owner-change
reason can be reused. Removal metadata is keyed only by explicit
`remove_contract_keys`, including contracts swallowed by a slice deletion. Unit
schemas and runtime admission bind each baseline to its original key or validated
current disposition holder. Witness references grant no write authority.

The guard checks original identity/history, complete dispositions, real active
witnesses, stage availability in actual prerequisite closure, and preserved typed
applicability. Changed prose, helper selection and decomposition alone do not
hard-block. Optional unmodeled typing stays visible. Retirement/correction quotes
establish provenance only. Real user withdrawal and draft correction are supported,
with the original claim retained in history.

Every baseline has a separate mandatory semantic subject. Review receives exact
original statement and mechanism, origin, disposition, current witnesses, stage
and catalogue references. Whole-record aliases are same-kind, direct and
hash-checked. The independent semantic reviewer still judges whether meaning,
promised timing and actual user intent authorize replacement/correction/retirement.
Its assertion alone is not deterministic authorization or execution evidence.

Request limits remain unchanged. Payloads are bounded projections, with no full
candidate/compiler histories sent. A budget overrun holds before dispatch without
omitting evidence. Offline tests and fixture measurements are structural/protocol
proof only; neither v3 review nor this guard has live model-quality coverage.

Router context uses a lossless, router-only encoding for equal complete same-key
statements/mechanisms already present in its acceptance directory or completed
mechanisms, and equal earlier retained records. Every claim remains present.
Local typed references carry content hashes; original changed evidence stays
inline. A strict decoder verifies identity, kind, ordering and the complete
round-trip. Unit generation continues to receive its exact scoped claim bodies.

New requests derive a bounded immutable projection of prior *proposed canonical
dispositions* from the exact pinned predecessor's audit, after matching original
claim identity/hash/binding. This keeps pending retirement and renamed-holder
mappings usable without inventing approval or restoring inactive contracts.
They remain fresh semantic subjects. Inactive original identities can receive
acceptance-disposition metadata only when server scope binds them to that claim.

A unit explicitly assigned only `acceptance_changes` may record a real changed
disposition without changing Project or revision. Its checkpoint is labeled
audit-only; repeated identical dispositions and attempts to satisfy substantive
statement/mechanism repairs with metadata are rejected. The writer transaction
replays the exact assigned checkpoint. Review scope/receipt is invalidated even
when the planning hash is unchanged. No other NO_PROGRESS exception is added.
Question and no-op direct write paths enforce the same entry/audit seal before
any canonical question or candidate write.
