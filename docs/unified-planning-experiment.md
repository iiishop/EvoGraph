# Unified planning experiment

This branch is an opt-in prototype. Turn on **统一规划** for a project. Existing projects keep their legacy planning route unless explicitly enabled. Nothing here merges into the published main branch.

## Product flow

Describe an outcome or a change in the same composer. The agent incrementally builds a visible, read-only candidate. You can inspect its requirements, contract links, architecture and delivery steps while the canonical plan stays available. Routine planning does not require manual approval of each item or of every completed turn.

After generation, EvoGraph finalizes dependencies and target membership **inside the candidate**, checks exact references and source history, then makes a separate bounded semantic challenge. A result with clear structural checks and no issue found by the semantic challenge is automatically applied in one transaction. This is not proof of coherence. A failed, uncertain, interrupted or unavailable review retains the candidate and its specific findings without applying partial planning edits. Continue through the composer to repair it; an explicit validation retry can reuse an unchanged candidate. Discarding a candidate is separate from undoing an applied plan.

## Representation and enforceable properties

- User source records retain exact input text, source-turn identity, saved message identity, selected reference snapshots and observed read-tool evidence. Inherited plans are labeled `legacy`, not retroactively presented as user quotations
- Requirement anchors reference exact source substrings. When continuing an unfinished candidate, newly extracted requirements may explicitly cite its saved, not-yet-applied user sources; arbitrary old committed sources cannot be reintroduced that way. Retirement still needs the current input quote. Existing anchors cannot be overwritten or removed. A changed direction can retire a requirement with a new user-source quote and reason; its history remains. Re-enabling is a new source identity
- Request-scoped process constraints (for example, only planning or no online investigation) are stored separately from product requirements. They are anchored to their exact source request, do not count as product acceptance, and do not silently become permanent requirements. The reviewer challenges this classification and the meaning of later continuation/replacement requests. A failed research attempt is still visible in the activity audit
- Behavior revisions remain the single canonical acceptance text. A binding associates the exact behavior revision with source requirements, chosen mechanism, architecture components, and other behavior keys required before its slice is acceptable
- Every active behavior must be traced, active requirements need final-target coverage, referenced components must exist and be mapped, and declared required behaviors must belong to the same slice or prerequisite closure
- Changing a bound mechanism or requirement mapping also creates a behavior revision, so old evidence cannot certify the revised contract merely because its short acceptance sentence stayed unchanged
- Implementation and external acceptance exports carry these same source anchors, bindings and needed contracts

These are data and traceability guarantees. A matching quotation is not proof of authorization to weaken a requirement. A complete set of links is not proof of entailment, consistency, feasibility or good architecture.

## Validation, budget and provenance

The generator uses the normal provider and existing safe planning/read tools through a scoped staged-service facade. No execution, credential, settings, repository-write or claim tool is added. Normal generation uses `submit_plan_delta`, a shallow ID-linked record protocol compiled into the existing `PlanPatch`: source requirements, process constraints, contracts, slices, components and relations. Acceptance is written once in its contract. Changing one contract or one slice title does not resend other acceptance. Rich display/history objects are built by the application; unchanged records are not resubmitted. Unknown fields, incorrect types, explicit nulls, broken references and malformed JSON are rejected, never repaired or guessed. Advanced explicit architecture metadata changes allow legacy groups, source references, risks and quality scenarios to evolve without silently dropping them. Compilation input, protocol version and compiled-structure hash share the candidate checkpoint; this hash is distinct from the complete candidate hash. There are at most two initial generation calls (one optional evidence-reading call, then the patch). This is enforced by changing the available tool registry: the second call has only patch, validation and genuine-question tools; continuation and repair start with that synthesis-only registry. Search cannot occupy another generation round. There is one repair call and at most two independent semantic challenges, with an overall ceiling of five admitted requests. A successful patch ends the generator pass after its complete response, without an extra narration call. The per-turn normalized messages+tools input budget is 384 KiB, with at most 128 KiB per request, 96 KiB of output text/arguments per request and 180 seconds per invocation. Six distinct source files may be read in an initial pass. Malformed/unavailable challenge results stop automatic publication rather than starting an unbounded retry chain.

The challenge receives the complete active candidate, current architecture, prior canonical plan, exact source records, selected reference snapshots, observed source/research evidence and required review subjects. It does not receive the generator's self-justification conversation. Packets over 192,000 UTF-8 bytes are explicitly unsupported; actual dispatch is additionally constrained by the 128 KiB request budget including the system prompt/schema and the remaining cumulative budget. Inputs are never silently truncated into a clearance. Image-grounded independent review is not supported in this prototype and fails closed.

Each review input is durably captured before the provider call, together with candidate hash, base revision, baseline and checker version. Server-authored validation receipts separate deterministic structural checks, fallible model opinion and implementation execution in this planning turn. The implementation layer always says this turn did not run implementation/acceptance; it does not erase earlier evidence. A compact expandable UI shows these three layers, binds receipts to the exact candidate hash and binds an applied result to its canonical revision. Missing/old/no-op receipts do not become a successful current review. Review items label their basis as model inference, model citation of source text, or an existing execution record. Existing execution IDs are strictly read-only references to records already in this project matching its current complete baseline, fingerprint, active behavior identities and architecture revision; PASS/FAIL/ERROR are preserved as recorded, not promoted. Eligibility proves only record identity/applicability, not that its content is true or that this turn executed anything. There is no automatic probe library or model-code execution in this prototype. Responses must echo the exact hash and cover the exact subject set. The UI calls a supported result **未发现问题**, never verified correctness. The provider can still miss a contradiction. Structural checks and model judgment are separate from actual implementation evidence.

Admitted request attempts, settings-stream invocations, whether an HTTP response was received, normalized prompt/schema/output byte counts, observed token usage and elapsed time are retained per candidate. Admission or a stream invocation alone is not a billable model request; the UI labels these as request attempts. Byte budgets describe application messages and tools, not exact adapter HTTP framing or provider tokenization. Provider numeric usage details, including cache counters when returned, are preserved. Cumulative usage counters are de-duplicated per invocation; Anthropic input/output counters remain separate. Token usage is explicitly unknown when the provider does not return it; no price estimate is invented. Every tool attempt is durably recorded before parsing, including the final failed attempt. Exact generation inputs, bounded raw output text/tool arguments and exact reviewed packets are retained. Raw output audit marks any byte-limit omission explicitly. Adapter request controls and unset completion limits, finish/stop reasons and termination markers are recorded separately from a normally drained stream. Known output limits, missing finish/terminal markers or unsupported choices stop publication; even valid tool JSON alone cannot waive an incomplete provider response. The generic compatible adapter does not assume a service-specific completion limit or strict-schema capability, and this experiment does not increase its defaults. Context-independent review identity includes the complete candidate; a separate planning fingerprint excludes audit-only tool activity solely to prevent a no-op repair from triggering another semantic review.

## Atomicity and recovery

Candidates live in a separate SQLite table and do not advance canonical project revision. Candidate checkpoints survive interruption/reopen. Application re-reads the durable candidate and validation, then uses one SQLite transaction to compare the canonical base revision, publish planning fields, mark the candidate applied and write the turn receipt. Messages and ordinary read activity are not part of that planning transaction.

The commit boundary includes target, architecture, milestone graph, behavior history and contract sources/bindings. Baseline identities, execution evidence, repository identity and settings cannot be written through the candidate facade. Normal external implementation/acceptance remains separate.

A cancellation before commit retains an uncommitted candidate. A cancellation or presentation failure after commit is recovered from the durable applied receipt. A concurrent canonical change blocks publication. Stale candidates are not silently rebased; inspect/discard the stale candidate before generating against the newer plan. Question publication/consumption and candidate-base advancement are atomic, and discarding an old candidate cannot clear a newer question.

The two experimental Project fields are stored in an additive sidecar table; canonical project JSON remains readable by the published main schema. Only rows containing earlier experimental fields are migrated, preserving other content and revisions. Legacy planning mutation APIs are blocked for enabled projects. Verification-only agent turns keep their investigation tools but cannot use planning mutators. Explicit source-analysis requests use a separate restricted read/reconstruction path (six rounds and sixteen tool calls), preserving the existing atomic source-capability reconstruction workflow. Its questions retain the source-analysis operation identity across resumption; it cannot create future-plan milestones or revise target/architecture. Existing projects, behavior IDs/history, execution evidence and current main flows remain compatible; enabling the experiment does not fabricate a semantic certificate for prior plans.

## Known limits

- This is a small-project prototype, not a universal natural-language theorem prover
- Legacy migration requires tracing inherited active contracts, which can be more work than a local edit
- A semantic challenge by the same saved provider is independent in context, not independent training or guaranteed independent reasoning
- Image-grounded review and oversized complete review packets are explicit unresolved states
- Candidate revision numbers are internal checkpoint revisions; canonical revision advances once for an applied planning aggregate
- Retained candidates are local working material. They do not constitute completed implementations, passing tests, or permission to weaken the user's original goal

## Field-level evolution and current evidence

The `plan-delta/v2` contract record uses a stable key plus only changed fields for an active contract. Omitted owner, statement, mechanism, acceptance scope and relation lists retain their exact stored values. A link-only requirement replacement therefore does not require regenerating acceptance prose. Explicit values replace a field; `[]` clears optional component/prerequisite links, but required text and requirement coverage cannot be cleared. New or explicitly restored inactive contracts require their complete required fields. A real active-owner migration additionally needs `owner_change_reason`; this records intent, not proof that the move is semantically appropriate. Unknown fields, null, stale compiler inputs and invalid final references still reject the whole private compilation.

Compiler audits bind the exact project, input revision and planning hash, compiled structure, resulting checkpoint revision/hash, and a server-computed before/after field diff. They preserve the v1 historical audit rather than rewriting it. Review packets independently compute the net canonical-to-candidate contract delta from current project objects and bind its exact revisions/hashes. They do not trust model-authored change descriptions or reuse an old compilation diff after a repair. These records highlight new promises and ownership changes; they do not determine whether a sentence belongs to an owner or follows from a mechanism.

The strict published-main Attachment schema has only a stored excerpt. An attachment at the historical 60,000-character clipping boundary cannot be declared complete, including an exactly-sized excerpt whose completeness is unknown. Selected such sources are retained with a clear failure before any provider call; historical snapshots and read-reference evidence are also checked before review. The prototype does not enlarge the context or alter that legacy schema. Shorter extracted text is not proof that PDF extraction captured all visual meaning. Previously committed clipped sources remain an explicit unresolved limitation rather than receiving a retroactive certificate.

Two real provider turns on the same small CLI planning project exercised initial creation and later batch evolution. Each used two HTTP responses and applied one atomic aggregate. The evolution preserved stable behavior keys, immutable source/history records and three unrelated active revision IDs while replacing three user requirement anchors and four related contract revisions. This demonstrates the workflow on those inputs, not generally reliable semantic judgment. Independent inspection found a retained valid-long-leading-zero parsing defect, an added CLI line-output promise in a pure-core acceptance, and stale architecture wording despite the model reporting no issue. This version is an experimental prototype, not production-ready. The subsequent field-patch regression tests replay saved real inputs and generated deltas locally; no provider rerun or semantic-success claim is implied by those deterministic passes.

The final branch review also exercised two-window candidate disposal and source-analysis question retries. Durable `applied`/`discarded` records now reject late save, question, no-op and publication paths under the SQLite writer lock. A running stream recovers that terminal record instead of reviving it; a successful publication with a lost acknowledgement reuses its durable receipt, and a no-op remains unchanged. Late observed request/output/tool audit differences are stored in a separate explicitly partial audit event without changing the terminal plan/hash. An audit-write failure is reported rather than relabeled as complete capture. A source-analysis answer whose question was consumed before failure retains its admitted operation identity in the session's failed draft and explicit retry; a new edited prompt does not inherit it. This does not promise draft recovery after browser restart or an operation identity never received in a `started` event.
